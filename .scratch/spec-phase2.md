# Спек: Фаза 2, шаг 1 — заказы, тепловая карта, расписания показов, дневные лимиты

Дата: 2026-10-14. Статус: на ревью владельца. Основа: .scratch/spec.md (фаза 1), .scratch/facts.md (живые факты API).
Решения владельца: скоуп «расписания → биддер»; часы — из заказов WB; токены будут с «Чтение и запись».
Автономия: **«добро → авто» (дефолт, принят координатором без ответа владельца — владелец может ужесточить)**: расписание подтверждается кнопкой «Применить», дальше пауза/старт работают сами; первая неделя — dry_run; kill-switch; полный журнал.

## Problem Statement

Реклама крутится 24/7, включая мёртвые ночные часы, и сливает бюджет, когда покупателей нет. Вручную паузить/запускать кампании по часам невозможно. Нужен контроллер: собирает заказы WB с точностью до часа, показывает активные часы, по подтверждённому расписанию ставит кампании на паузу и возвращает, плюс дневные лимиты с автостопом.

## Solution

В существующем Bider (подход A — тот же процесс): новый цикл сбора заказов (statistics-api, 1/мин, инкремент), страница «Часы» с тепловой картой заказов по часам, страница «Расписания»: генератор часов из тепловой карты + ручная правка, дневной лимит на кампанию, кнопка «Применить». Контроллер (1/мин) применяет расписания: пауза/старт через advert-api, дневные лимиты CPC — нативно через daily-limits API, CPM — контролем расхода. Предохранители: dry_run, kill-switch, дедуп, журнал каждого действия.

## User Stories

1. Как владелец, я хочу, чтобы Bider собирал мои заказы WB по часам, чтобы видеть активность покупателей.
2. Как владелец, я хочу тепловую карту заказов по часам (7/30 дней) по кабинету, чтобы видеть, когда реально покупают.
3. Как владелец, я хочу на странице «Расписания» видеть для каждой кампании сгенерированные активные часы и отредактировать их вручную.
4. Как владелец, я хочу задать кампании дневной лимит расхода, чтобы бюджет не сливался за день.
5. Как владелец, я хочу кнопкой «Применить» включить расписание кампании, чтобы контроллер сам ставил её на паузу вне активных часов и запускал в активные.
6. Как владелец, я хочу режим dry_run, чтобы первая неделя контроллер только ЖУРНАЛИЛ действия, не применяя.
7. Как владелец, я хочу kill-switch «Стоп всё», чтобы мгновенно запретить контроллеру любые действия (и «Возобновить»).
8. Как владелец, я хочу журнал всех действий контроллера (что, когда, результат), чтобы понимать, что он сделал.
9. Как владелец, я хочу, чтобы CPC-лимиты ставились нативно через WB (daily-limits), а CPM контролировались расходом, чтобы использовать механики платформы.
10. Как владелец, я хочу, чтобы кампания со CPM-лимитом автоматически ставилась на паузу при достижении дневного лимита и возвращалась после 00:00 МСК.
11. Как владелец, я хочу, чтобы контроллер не дёргал кампанию чаще одного переключения в час, чтобы WB не считал это подозрительным.
12. Как владелец, я хочу баннер режима (dry_run/live) на странице расписаний, чтобы всегда видеть, применяются ли действия.
13. Как владелец, я хочу, чтобы сбор заказов переживал простоя и догонял историю (до 90 дней), чтобы тепловая карта не рвалась.
14. Как владелец, я хочу, чтобы при 3 подряд ошибках контроллер кабинета вставал на паузу, как сборщик.

## Implementation Decisions

- **Заказы**: statistics-api.wildberries.ru `GET /api/v1/supplier/orders` (категория «Статистика»), flag=0 инкремент по lastChangeDate, dateFrom RFC3339 в МСК; лимит 1/мин (Personal). Дедуп по `srid` (PK). Хранение: `orders(srid text pk, cabinet_id, nm_id bigint, date date, hour int, price_kopecks bigint, date_time timestamptz, is_cancelled bool)`. Отменённые/возвраты: помечаем и вычитаем из агрегатов. Данные WB хранит ≤90 дней.
- **Тепловая карта**: агрегат из orders GROUP BY hour (по МСК), период 7/30 дней; Chart.js bar; страница `/hours?cabinet=`.
- **Расписания**: `schedules(cabinet_id, advert_id, hours jsonb — массив 24×0/1, daily_limit_kopecks bigint null, enabled bool, updated_at, applied_at)`. Генератор: часы, покрывающие `coverage`% заказов (по умолчанию 90%, настройка на кабинет в `app_settings`), минимум 6 часов.
- **Контроллер**: цикл 60с на кабинет; для каждой enabled-кампании: желаемое состояние по текущему МСК-часу (вкл/выкл) и по лимиту (перерасход → пауза до конца суток); перед действием сверяет фактический статус (adverts ids=[id], 1 запрос); дедуп: не чаще 1 переключения на кампанию в час; все действия — в `controller_log(id, cabinet_id, advert_id, action pause/start/limit, result, detail, created_at)`; при dry_run — запись со status="dry" БЕЗ вызова записи в WB.
- **WB-клиент**: новые методы `pause(advert_id)`, `start(advert_id)` (GET /adv/v0/pause|start — точные параметры подтверждает спайк-2 в песочнице advert-api-sandbox + заголовки лимитов), `daily_limits_get/put` (только Personal-токен), `orders(date_from)` — отдельный клиент statistics-api (другой хост, лимит 1/мин).
- **CPC-лимиты**: PUT daily-limits (нативно, WB сам остановит). **CPM**: контроллер сравнивает сегодняшние траты (stats за сегодня, обновление раз в 20 мин) с daily_limit_kopecks; перерасход → пауза до 00:00 МСК; после полуночи — старт если час активный.
- **Kill-switch**: `app_settings` key `controller_kill_switch`; при true контроллер только логирует «skipped (kill-switch)». Кнопки в UI.
- **Предохранители**: дедуп 1 переключение/час/кампанию; 3 подряд ошибки на кабинете → пауза контроллера кабинета 15 мин; действие только по кампаниям из нашей БД.
- **Режим**: `app_settings` key `controller_mode` = dry_run|live (глобально на MVP; в dry_run все действия пишутся в журнал со status="dry").
- **UI**: `/hours?cabinet=` — тепловая карта; `/schedules?cabinet=` — баннер режима, kill-switch, таблица РК (часы чекбоксами 0–23, лимит, «Применить»), журнал контроллера (последние 100).
- **Read-only фазы 1 не нарушается**: всё пишущее живёт в контроллере фазы 2 и по умолчанию dry_run.

## Testing Decisions

- Генератор часов (coverage, минимум) — чистые функции, табличные тесты.
- Контроллер: фейковый клиент + фейковое время; проверяются: дедуп, kill-switch, dry_run (нет вызовов API, есть журнал), CPM-стоп по лимиту, старт после полуночи, 3 ошибки → пауза кабинета.
- Orders-сбор: фейковые ответы (инкремент, дедуп srid, отменённые).
- Страницы: TestClient smoke (баннер режима, kill-switch, применение).
- Живые write-вызовы (pause/start/daily-limits) — только после спайка-2 в песочнице и отдельно подтверждённого добро владельца на боевую кампанию.
